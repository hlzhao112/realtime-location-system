# 预制梁台车追踪系统 · 实现方案（Protocol / 技术方案）

版本：v1.0 · 日期：2026-08-23  
依据：PRD v0.5、Omada 交互原型 v7、三份现场 Excel 模板  
本版范围：**登录、项目看板、新建/编辑/复制项目（三步向导）、项目信息（基本信息 / 映射表 / 报文模板）、设备上报与解析引擎**。  
明确预留、本版不做页面：**项目内主看板、原始数据监控、系统日志**（接口与表结构已预留）。

---

## 1. 目标与约束

一句话：台车上的读卡器读到地面 RFID（EPC）后上报后台；后台按「读卡器 → 台车、EPC → 产线/工序/区域」解析出位置；管理员在 Web 上按项目管理映射与推送配置。

硬约束：

- 多项目隔离，全部业务数据归属 PID。
- 映射不写死：产线 / 工序 / 区域由项目自行导入。
- 映射链路为两级：`位置 → 蓝牙标签编号 → 多个 EPC`；读到任一 EPC 即可定位。
- 上报量会随台车数线性增长，接入路径必须与配置/查询路径隔离，避免互相拖垮。
- 本版不做主看板 / 原始数据页 / 系统日志页，但引擎要把「最新位置」算出来并落库，后续页面只读即可。

---

## 2. 总体架构

```
台车读卡器 ──HTTP POST──► Ingest Gateway (FastAPI, 仅入队)
                              │
                              ▼
                        Redis Stream (ingest.raw)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              Parse Worker         (预留) Persist Worker
              EPC/读卡器查表            原始 HEX 落库
              纠偏 / 补发钩子          系统日志钩子
                    │
                    ▼
              Redis Hash (location:{pid})
              PostgreSQL (latest_location)
                    │
                    ▼
         (预留) Push Worker → 客户 Token / 上报接口

管理员浏览器 ──REST──► Admin API (FastAPI)
                         │
                    PostgreSQL
                    项目 / 映射 / 模板 / 账号
```

分层原则：

| 层 | 职责 | 失败策略 |
| --- | --- | --- |
| Ingest | 鉴权、校验、入队，**不做查表** | 满队列返回 429，不阻塞其他项目 |
| Worker | 解析、更新最新位置 | 单条失败记死信，不回压接入 |
| Admin API | 登录、项目、映射、模板 | 与 Ingest 分路由，可独立限流 |
| Web | Omada 风格管理端 | 只打 Admin API |

本版用 **单进程 FastAPI + 后台 asyncio 消费者** 即可跑通；生产可把 worker 拆成独立进程水平扩展。Redis 不可用时，接入接口降级为同步落库（性能下降但业务不中断）。

## 3. 上报协议（设备 → 我方）

### 3.1 接入方式

`POST /api/v1/ingest/report`

鉴权（二选一，优先 Token）：

- Header `X-Ingest-Token: <项目 ingest_token>`
- 或 `Authorization: Bearer <ingest_token>`

Token 在项目创建时生成，仅管理员可见。读卡器固件只需带 Token + 设备 ID，不必知道 PID。

### 3.2 报文体

```json
{
  "deviceId": "LYG11",
  "ts": "2026-08-23T16:48:01.235+08:00",
  "hex": "E2806894000040358004310A E2806894000050358004350A",
  "epcs": ["E2 80 68 94 00 00 40 35 80 04 31 0A"],
  "sportState": "moving"
}
```

字段约定：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| deviceId | 是 | 读卡器 ID，对应台座映射表「台座安装LYG」列 |
| ts | 否 | 设备侧识别时间；缺省用服务端接收时间 |
| hex | 否* | 原始 HEX，空格可有可无；用于后续原始数据页 |
| epcs | 否* | 已切分的 EPC 列表；与 hex 至少有一个 |
| sportState | 否 | `moving` / `still`；缺省由引擎按位移推断 |

`*` hex 与 epcs 必须至少提供一个。同一次上报可带多组 EPC（PRD：同一时刻可识别 2～3 组，完整保留）。

响应：

```json
{ "accepted": true, "queued": 1, "id": "01J..." }
```

HTTP **202**。成功只表示入队，不表示解析成功。解析结果走内部状态，本版不在接入响应里回传位置，避免设备侧耦合业务。

### 3.3 节流与保护

- 单项目默认 200 req/s，超限 429。
- 单报文 EPC 数上限 32。
- 报文体上限 32 KB。
- Redis Stream 按项目 maxlen ≈ 100_000，旧消息淘汰；最新位置以 Redis Hash + PG upsert 为准。
- 幂等：同一 `deviceId + ts + hex` 在 10 分钟窗口去重。

### 3.4 EPC 规范化

入库与查表前统一：

1. 去空白、去冒号、大写。
2. 允许带空格的现场写法 `E2 80 68 94 ...`。
3. 查表用规范化值；展示保留导入时的原始空格格式。

## 4. 映射模型

```
Project
  └─ Line (生产线 / 生产线ID)          项目内 ID 唯一
       └─ Procedure (工序 / 工序ID)    同产线内编码唯一；顺序 = 列表序
            └─ Area (区域 / 区域ID)
                 └─ TagNo (蓝牙标签编号，默认 3 个/区)
                      └─ EPC[]         一个编号对应多条

Project
  └─ Trolley (台座名称 / TZ_xxx / 读卡器ID)  台车编号、读卡器均项目内唯一
```

解析：

```
deviceId → Trolley
任一 EPC → TagNo → Area → Procedure → Line
⇒ 台车当前位置 = (trolley, line, procedure, area, ts)
```

工序顺序不单独存 JSON，只存 `sort_order`。纠偏 / 补发（预留）按该顺序判断「蒸养后必须走完本产线」。

## 5. Excel 导入协议

### 5.1 映射表一（双文件，缺一不可）

**① 位置-编号映射表**（现场文件列名兼容）

| 列 | 兼容表头 |
| --- | --- |
| 生产线 | 生产线 / 产线 / 产线名称 |
| 生产线ID | 生产线ID / 产线ID / 产线编码 |
| 工序 | 工序 / 工序名称 |
| 工序ID | 工序ID / 工序编码 |
| 区域 | 区域 / 区域名称 |
| 区域ID | 区域ID；若表头写成第二个「区域」，按第 6 列视为区域ID |
| 蓝牙标签编号 | 蓝牙标签编号 / 标签编号 / No. |

一行 = 一个「区域 + 一个编号」。同区域通常连续 3 行。工序顺序 = 该产线在文件中的首次出现顺序。

**② 编号-映射表**

| 列 | 说明 |
| --- | --- |
| No. | 同一编号只在首行填写，下方留空表示延续 |
| EPC | 实际值，可带空格 |

拼接键 = 标签编号。位置表引用但编号表没有 → **阻止导入**，定位到「位置表 第 N 行 · 列」。编号表有但位置表未引用 → **提示备用，不导入**。

### 5.2 映射表二（单文件）

**台座编号映射表**（港台座编号映射.xlsx）

| 列 | 兼容表头 |
| --- | --- |
| 台座名称 | 台座名称 |
| 编号 | 编号 / 台车ID / TZ |
| 台座安装LYG | 台座安装LYG / 读卡器 / 读卡器ID / 设备ID |

跳过空行，去首尾空格。编号或读卡器重复 → 阻止并定位行。

### 5.3 导入交互（与原型一致）

模板下载 → 上传 → 表头/列数校验 → 解析预览 + 统计 → 三态校验（通过 / 提示 / 阻止）→ 变更对比 → 二次确认整表覆盖。

本版覆盖策略：**整表覆盖**（PRD 待确认 #14 的默认）。

## 6. 解析引擎（本版落地 + 预留钩子）

热路径只做：

1. 规范化 EPC，命中项目映射缓存（进程内 + Redis）。
2. deviceId 命中台车。
3. 写出 `latest_location`（来源 = `auto`）。
4. 同台车同区域、仅时间不同：默认保留最新一条状态，不生成历史推送（推送记录页预留）。

预留、本版不执行业务副作用：

- 纠偏（蒸养后禁止跨产线）
- 补发 12 条缺失工序
- 连续补发计数
- 自动 / 手动 / 批量推送客户接口
- 原始 HEX 详情页、系统日志页

钩子位置：`backend/app/engine/hooks.py`，后续直接填实现即可。

```
登录
 └─ 项目看板          实现
     ├─ 新建/编辑/复制  三步向导（Step3 可跳过）
     └─ 进入项目
```

## 8. 数据存储

| 存储 | 用途 |
| --- | --- |
| PostgreSQL | 用户、项目、映射、模板、最新位置；预留 raw_report / push_record / sys_log 表 |
| Redis | ingest Stream、EPC 倒排缓存、最新位置 Hash、Token 会话 |
| 本地 templates/ | 三个标准 Excel 模板 |

最新位置表按 `project_id + trolley_id` 唯一约束，上报只做 upsert，避免台车增多后无限膨胀。

---

## 9. 安全

- 管理员账号密码 bcrypt；会话 JWT（默认 12h）。
- AppSecret、ingest_token 库内存储，接口不回显明文（ingest_token 仅在首次创建/重置时返回一次）。
- 项目用户角色本版不做（与 PRD 一致）。
- CORS 仅开放管理端源。

---

## 10. 容量估算与扩展

假设：200 台车 × 每分钟 1 次上报 × 3 EPC ≈ 10 条/秒，远低于单节点 FastAPI + Redis 能力。  
风险点不是 QPS，而是「同步解析 + 同步推客户 + 同步写大表」绑在一起。因此本版把接入与解析拆开。

台车到 2000、上报到 1 秒/次时：

1. 增加 ingest worker 副本（消费同一 Stream group）。
2. raw_report 按日分区（表已预留 `report_day`）。
3. 推送独立队列，失败重试不回压解析。

## 11. 本版验收

- 管理员可登录，看到项目看板。
- 三步向导可建项目；Step2 可用三份真实模板导入并预览/校验/覆盖。
- 项目信息可单项编辑基本配置、映射（含工序拖拽顺序、产线/工序就地编辑）、报文模板。
- `POST /api/v1/ingest/report` 入队后，最新位置可被内部 API 读到。
- 主视图 / 原始数据 / 系统日志为占位，不阻塞导航。
